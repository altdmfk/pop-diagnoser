FIDO2 PoP 요청 진단기

기반 논문: “Design and Performance Analysis of a FIDO2 Hardware-Isolated Key-Based Proof-of-Possession Reverse Proxy Gateway” (논문 및 게이트웨이 프로젝트)

이 앱은 FIDO2 PoP 게이트웨이를 연동하는 클라이언트 개발자가 서명 불일치로 401·403·400 오류를 겪을 때, 논문의 5단계 검증 규격과 14개 가설 역추적으로 어느 단계에서 어떤 규칙 차이 때문에 거절되었는지 찾아주어 원인 분석과 신속한 문제 해결을 돕습니다.

일반 인증 토큰은 탈취되면 다른 기기에서도 그대로 재사용할 수 있습니다. 이를 막기 위해 FIDO2 PoP(소유 증명) 게이트웨이는 클라이언트가 요청을 보낼 때마다 HTTP 요청 내용(메서드, 주소, 시각, 난수, 본문 해시)을 개인키로 직접 서명하게 하고, 서버가 등록된 공개키로 그 서명을 확인합니다. (서버 DB 조회가 필요한 Nonce 중복 검사와 JWT 바인딩 확인은 오프라인 진단에서 제외됩니다.)

실제로 요청을 보낸 메서드(POST, GET 등)와 전체 주소입니다. 서명할 때는 대문자 메서드를 쓰고, 주소 뒤의 쿼리(?c=3&a=1&b=2)도 정렬하지 않고 보낸 순서 그대로 넣어야 합니다.
서버로 보낸 본문 원문입니다. 공백이나 줄바꿈이 한 글자라도 달라지면 본문 해시값(Body-Digest)이 바뀌어 5단계에서 실패합니다. (참고: 브라우저 입력창은 HTML 표준에 따라 직접 입력한 줄바꿈을 LF(\n)로 정규화하며, 줄바꿈 차이로 인한 해시 불일치는 5단계 newline-crlf 가설이 양방향으로 진단합니다.)
같은 요청을 가로채서 다시 보내는 공격(재전송 공격)을 막기 위해 요청마다 새로 만드는 1회용 문자열입니다.
서명을 만든 시각(초 단위 Unix 시간)입니다. 검증 설정 탭의 '평가 기준 시각'과 비교해 60초 넘게 차이 나면 2단계에서 만료 처리됩니다.
요청 본문(Body)을 SHA-256으로 해시한 값입니다. 'sha256=' 뒤에 64자리 소문자 16진수(Hex)를 붙이며, 서명할 문자열의 마지막 줄에도 들어갑니다.
요청 항목들을 줄바꿈(\n)으로 이어 붙인 문자열에 ECDSA P-256 개인키로 서명한 값입니다. r(32바이트)과 s(32바이트)를 합친 64바이트 Raw 형식을 Base64url로 인코딩해야 합니다.
클라이언트의 개인키와 짝을 이루는 ECDSA P-256 공개키(SPKI PEM 형식)입니다. 게이트웨이와 이 진단기는 개인키 없이 공개키만으로 서명이 맞는지 확인합니다.
게이트웨이가 요청을 검사하는 기준 시각(초 단위)입니다. 이전에 캡처한 요청을 진단할 때는 요청의 Timestamp와 비슷한 값으로 맞춰 두면 만료 오류 없이 서명을 확인할 수 있습니다.
브라우저 개발자 도구(Network 탭 → 요청 우클릭 → Copy as cURL)에서 복사한 명령어나 HTTP 요청 원문을 붙여넣으면 메서드, URL, 본문, 서명 헤더 4종을 한 번에 채웁니다. (브라우저 입력창은 직접 입력한 줄바꿈을 LF로 정규화하며, cURL의 $'...\r\n...' 이스케이프 본문은 원본 CRLF가 보존됩니다.)
기존 입력값이 있습니다. 덮어쓰시겠습니까?
임시저장소 (슬롯 1~5)
현재 입력된 요청, 서명 헤더, 공개키, 평가 기준 시각을 브라우저 저장소(localStorage)에 5개까지 저장해 두고 비교할 수 있습니다.

왜 ECDSA P-256 서명을 사용하나요?

매 API 요청마다 헤더에 서명을 담아 보내야 하므로 서명 크기가 작을수록 네트워크 부담이 줄어듭니다.
64바이트 길이의 ECDSA P-256 서명을 사용하면 RSA-2048을 쓸 때보다 서명 헤더 전체 크기를 약 절반(499 Bytes → 243 Bytes, 51.3% 감소)으로 줄일 수 있습니다.
