# PoP Diagnoser 기술 과제 해결 및 리팩토링 기록

이 문서는 FIDO2 PoP(Proof-of-Possession) 게이트웨이의 클라이언트 오프라인 진단기(**PoP Diagnoser**)를 리팩토링하면서 해결한 핵심 기술 과제와 아키텍처 의사결정을 정리한 기록입니다.

실무 및 기술 면접 관점에서 중요한 5가지 기술적 도전 과제(바이너리 파서 정합성, BFS 가설 탐색 최적화, 웹 런타임 플랫폼 격차, 제로 트러스트 DOM 보안, 실무 중심 UX 개편)를 중심으로 다룹니다.

---

## 1. 암호학 규격 정합성 및 바이너리 파서 설계

### 배경 및 문제
- **DER/Raw 서명 규격 불일치**: FIDO2 PoP 게이트웨이는 IEEE P1363 규격(64바이트 Raw `r || s`)을 요구하지만, 대다수 암호화 라이브러리는 ASN.1 DER 형식(보통 70~72바이트)을 기본 반환합니다. 기존 진단기는 최소 길이 조건을 70바이트로 고정하여, `r` 또는 `s` 최상위 바이트가 `0x00`으로 패딩 생략된 유효한 68~69바이트 DER 서명을 처리하지 못했습니다.
- **파서 이원화로 인한 모순 판정**: 진단 파이프라인(`diagnose.js`)과 구조 분석 인스펙터(`inspect.js`)가 각자 독립된 정규식과 DER 파서를 사용하여, 동일한 서명과 공개키에 대해 판정 결과가 엇갈리는 문제가 있었습니다.
- **비밀키 노출 위험**: 테스트 서명 생성기에서 `extractable: true`로 키 쌍을 생성하여 브라우저 메모리 외부로 개인키가 노출될 수 있는 설정이었습니다.

### 해결 방법
1. **바이너리 파서 경계 정밀화 ([`js/core/ecdsa.js`](../js/core/ecdsa.js))**:
   - `parseDerSignature()`를 구현하여 8바이트 최소 헤더부터 가변 길이 long-form DER까지 정확한 오프셋(`offset = 2 + numLenBytes`)으로 파싱하도록 개선했습니다.
   - 선행 `0x00` 정규화 및 바이트 길이 검증(`1 <= len <= 32`)을 통해 68~72바이트 범위의 모든 유효한 DER 서명을 64바이트 Raw 포맷으로 변환하도록 정합성을 확보했습니다.
2. **단일 파서 파이프라인 통합 ([`js/core/inspect.js`](../js/core/inspect.js))**:
   - 서명 디코딩(`detectAndDecodeSignature`), 공개키 SPKI 파싱(`extractPublicKeySpkiBytes`), 비밀키 감지(`containsPrivateKeyMarker`)를 단일화하여 진단기와 인스펙터가 항상 동일한 기준을 적용하도록 했습니다.
3. **비밀키 보호 원칙**:
   - 비밀키(`PRIVATE KEY`) 입력 감지 시 즉시 파싱을 중단하고 `PRIVATE_KEY_REJECTED` 오류를 반환하며, WebCrypto 키 생성은 `extractable: false`로 고정하여 키 유출 가능성을 차단했습니다.

## 2. BFS 가설 탐색 알고리즘 및 상태 공간 최적화

### 배경 및 문제
- **순열 중복 및 연산 폭발**: 클라이언트가 범한 복합 실수(예: 메서드 소문자 + 쿼리 정렬 + 슬래시 누락)를 역추적하기 위해 최대 깊이 3의 너비 우선 탐색(BFS)을 수행합니다. 초기 구현에서는 순서만 다른 동일 가설 집합({A, B, C})이 6번 중복 탐색되고, 슬래시 추가 후 다시 제거하는 역연산 쌍이 큐에 들어가면서 비용이 큰 `WebCrypto.subtle.verify()` 연산이 불필요하게 반복 호출되었습니다.
- **다이제스트 복합 탐색 누락**: 5단계(본문 다이제스트)는 단일 가설만 순회하여 복합 실수(예: BOM 추가 + 대문자 Hex)를 감지하지 못했습니다.

### 해결 방법
1. **조합 인덱스(`startIdx`) 및 상태 캐시(`stateCache`) 도입 ([`js/core/diagnose.js`](../js/core/diagnose.js))**:
   - 탐색 큐에 조합 시작 인덱스를 부여해 순열 중복을 배제했습니다.
   - 상태 캐시(`canonical|sigHex`)를 도입하여, 이전 깊이에서 이미 도달한 상태(역연산으로 초기 상태로 회귀하는 경우 등)를 즉시 가지치기(Pruning)했습니다.
   - 동일 깊이에서 같은 정규화 문자열로 수렴할 때는 캐시된 검증 결과를 재사용하여 `verifySig()` 재호출을 억제하면서도, 동일한 결과를 내는 구분 불가(`indistinguishable`) 가설 후보 경로는 보존했습니다.
2. **4·5단계 독립 탐색 및 결과 병합**:
   - 5단계에도 최대 깊이 3의 BFS 조합 탐색을 적용하고, 4단계와 5단계가 동시에 실패한 경우 양쪽의 원인 조합을 독립 탐색하여 모두 화면에 출력하도록 개선했습니다.

## 3. 웹 플랫폼 런타임 격차와 바이트 정밀도 보장

### 배경 및 문제
- **Node.js와 브라우저 Base64url 처리 차이**: 길이가 4의 배수가 아닌 비정상 Base64url 문자열(`length % 4 === 1`)에 대해 브라우저(`atob`)는 예외를 던지는 반면 Node.js(`Buffer.from`)는 패딩을 유연하게 처리하여 런타임 간 진단 결과가 불일치했습니다.
- **HTML `<textarea>`의 줄바꿈 강제 정규화**: HTML 명세에 따라 브라우저의 `<textarea>`는 모든 줄바꿈을 `LF(\n)`로 자동 치환합니다. 이로 인해 cURL이나 원문 요청에 포함된 `CRLF(\r\n)` 바이트가 입력창을 거치면서 유실되어 본문 해시가 어긋나는 구조적 한계가 있었습니다.
- **JSON 편향 검사로 인한 비-JSON 진단 차단**: 게이트웨이는 본문을 순수 바이트 스트림으로 취급하지만, 진단기가 1단계 필수 헤더 확인 전에 `JSON.parse`를 먼저 수행하여 평문 로그나 Form 데이터 진단이 불가능했습니다.

### 해결 방법
1. **크로스 런타임 인코딩 계층 단일화 ([`js/core/encoding.js`](../js/core/encoding.js))**:
   - `base64UrlDecode()` 앞단에 엄격한 정규식과 길이 검사(`length % 4 !== 1`)를 추가하여, 브라우저와 Node.js 환경 모두에서 동일한 예외 및 오류 분기를 타도록 보장했습니다.
2. **메모리 원본 바이트 보존 구조 ([`js/ui/importer.js`](../js/ui/importer.js), [`js/ui/slots.js`](../js/ui/slots.js))**:
   - cURL/Raw HTTP 파서 및 슬롯 저장소에서 원본 본문을 별도 메모리 필드(`_rawBody`)로 관리하여 사용자가 입력창을 직접 수정하기 전까지 원본 개행(`\r\n`)을 보존하도록 설계했습니다.
   - 줄바꿈 차이로 인한 불일치를 양방향(`LF ↔ CRLF`)으로 감지하는 `newline-crlf` 가설을 지원하고 UI 안내를 추가했습니다.
3. **프로토콜 검증과 휴리스틱 검사의 역할 분리 ([`js/core/diagnose.js`](../js/core/diagnose.js))**:
   - 실행 순서를 `1단계(필수 헤더) → 입력 서식 검사 → 2~5단계 검증`으로 정상화했습니다.
   - JSON 문법 검사는 본문이 실제 JSON 패턴을 띨 때만 비차단 경고(`warnings`)와 위치 포인터(`▲`)로 안내하도록 변경하여 평문 본문 진단을 온전히 지원했습니다.

## 4. 보안 아키텍처: DOM XSS 원천 차단 및 UMD 모듈화

### 배경 및 문제
- **동적 HTML 조립으로 인한 XSS 취약점**: JSON 오류 힌트나 잘못된 HTTP 메서드 경고를 출력할 때, 사용자 입력 문자열을 이스케이프 없이 HTML 템플릿 리터럴로 조합해 `innerHTML`에 대입하던 코드가 존재했습니다.
- **환경 종속적 구조**: 로컬 `file://` 환경에서는 브라우저의 CORS 정책으로 인해 ES Modules(`import/export`)가 차단되어 실행되지 않는 제약이 있었습니다.

### 해결 방법
1. **DOM 조작 원칙 수립 ([`js/ui/render.js`](../js/ui/render.js))**:
   - 프로젝트 전반에서 `innerHTML`, `outerHTML`, `eval`, `new Function`, 인라인 이벤트 핸들러 및 `el.style.*` 조작을 완전히 배제했습니다.
   - 코어 엔진은 순수한 직렬화 가능 데이터 객체만 반환하고, 화면 렌더링은 `document.createElement`와 `textContent`로만 구성하여 XSS 가능성을 구조적으로 제거했습니다.
2. **무빌드 UMD 모듈 패턴 적용**:
   - 모든 모듈을 UMD(Universal Module Definition) 래퍼로 감싸, 번들러나 트랜스파일러 없이도 브라우저 전역(`window.PopCore`, `window.PopUI`)과 Node.js(`require()`) 테스트 환경 양쪽에서 동일한 소스 코드가 동작하도록 구축했습니다.

## 5. 실무 중심 UX 및 오류 안내 개편

### 배경 및 문제
- 기존 진단기는 `s > n/2 (High-S 서명)`, 타원곡선 방정식(\(y^2 \equiv x^3 - 3x + b \pmod p\)), `AlgorithmIdentifier SEQUENCE` 등 이론적 수식과 내부 용어를 그대로 출력하여, 실무 개발자가 구체적으로 무엇을 수정해야 하는지 직관적으로 알기 어려웠습니다.
- 과도한 장식용 이모지와 일관되지 않은 상태 표시로 인해 전문적인 개발 도구로서의 가독성이 떨어졌습니다.

### 해결 방법
1. **3단계 직관적 문구 구조 (상태 - 원인 - 조치)**:
   - 복잡한 수식을 배제하고 개발자가 즉각 조치할 수 있는 평이한 한국어로 개편했습니다. (예: High-S 서명의 경우 표준 통과 여부와 게이트웨이 거절 사유, 정규화 라이브러리 옵션 설정 가이드를 명시)
2. **장식 요소 정돈 및 전문적 UI 스타일링**:
   - 모든 장식용 이모지를 제거하고 텍스트 기반 상태 태그(`[정상]`, `[오류]`, `[경고]`)와 절제된 1px 보더 팔레트로 시각적 노이즈를 줄였습니다.
3. **슬롯 저장소 고도화 및 레이아웃 균형**:
   - 임시 저장 슬롯을 접이식 아코디언 패널로 전환하여 탭 간 높이 불균형을 해소했습니다.
   - 슬롯별 요청 요약(메서드, 경로, 바이트 크기, 서명 여부, 시각), 인라인 이름 변경, 덮어쓰기 확인, 네이티브 `title` 상세 미리보기를 추가했습니다.
4. **내부 식별자 불변 유지**:
   - 사용자에게 보이는 문구는 알기 쉽게 변경하되, `HIGH_S`, `POINT_NOT_ON_CURVE`, `INVALID_SPKI_DER` 등 내부 오류 코드와 가설 ID는 테스트 스위트 및 게이트웨이 규약과의 정합성을 위해 그대로 보존했습니다.
